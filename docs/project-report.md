## 1. Executive summary

Northstar Banking is a secure, role-aware retail-banking application that combines
**digital customer onboarding** with an **AI-assisted customer-support workspace**.
A public landing page introduces a focused catalogue of savings, credit-card,
personal-loan and fixed-deposit products. Customers complete an application,
upload KYC documents, submit it, track progress and view a masked illustrative
account overview. Reviewers process applications through a controlled workflow.
Support agents work a three-panel workspace whose summaries, replies and
recommendations are grounded in an approved knowledge base.

The solution is implemented as a **.NET 10 Clean Architecture backend** with a
**React 18 + TypeScript** single-page application. It uses SQLite for local
development and SQL Server for production profiles, JWT authentication with
rotating refresh tokens, role-based authorization, append-only audit and
workflow history, provider-abstracted document storage and email, and a
provider-abstracted AI layer supporting **Amazon Bedrock**, an OpenAI-compatible
adapter and a deterministic local fallback.

The AI capability is deliberately **assistive, bounded and auditable**. Ticket
content is treated as untrusted data, inputs are minimised, outputs are typed and
labelled with provenance, approved articles are cited with match reasons,
assistive classification never changes a recorded category, next-best actions are
generated by deterministic rules, and no AI output can approve an application,
change permissions or execute a privileged action without explicit human
confirmation.

The delivered solution builds with **0 warnings and 0 errors** and passes **228
backend tests**, **37 frontend unit tests** and **97 live HTTP smoke checks**. The
smoke suite was verified against a locally started API on an isolated temporary
database; the optional Docker Compose stack was not re-verified for the
knowledge-base and customer-ticket changes.

## 2. Business problem and context

### 2.1 Context

Retail-banking customer acquisition depends on two connected journeys:

1. **Onboarding** — product selection, eligibility, application completion, KYC
   document collection, review and decision.
2. **Support** — timely, accurate assistance while a customer is applying,
   waiting for a decision or using an account.

In many operating models these journeys are handled by separate systems and
teams. The result is fragmented customer context, manual hand-offs, inconsistent
communication and limited operational visibility.

### 2.2 Problem statement

The project addresses the following business problem:

> Customer onboarding and support are often disconnected, manually intensive and
> difficult to audit. Customers lack a clear digital journey, reviewers lack a
> controlled workflow, and support agents lack fast access to the full customer
> context. Existing support tools rarely provide consistent, safe assistance
> without increasing operational risk.

### 2.3 Specific business challenges

| Challenge | Business impact |
| --- | --- |
| Fragmented onboarding journey | Customers abandon applications or repeatedly contact support for status. |
| Manual document handling | Reviewers spend time checking completeness and validity; documents are hard to trace. |
| Inconsistent support responses | Agents give different answers for the same policy or process question. |
| Missing customer context | Agents must reconstruct application history and previous messages before responding. |
| Delayed escalation detection | Frustrated or urgent customers are not identified consistently. |
| Weak auditability | Changes, decisions and AI usage are difficult to reconstruct after the fact. |
| Security and privacy risk | Customer data, identity documents and support conversations require strict access control. |
| Slow adoption of AI | Uncontrolled generative AI can hallucinate, leak data or recommend unsafe actions. |

### 2.4 Business need

The organisation requires a solution that:

- Provides a coherent, secure digital journey from product discovery to decision.
- Gives reviewers a controlled, auditable workflow.
- Gives support agents complete context and consistent, safe assistance.
- Preserves human accountability for regulated or privileged decisions.
- Supports local development and production deployment without rewriting
  business logic.
- Remains maintainable, testable and extensible as providers and policies change.

## 3. Solution

### 3.1 Solution overview

Northstar Banking delivers an integrated platform with four role-specific
experiences:

| Role | Experience |
| --- | --- |
| **Customer** | Public landing page, product catalogue, application wizard, profile completion, KYC upload, status tracking, masked demo account overview and notifications. |
| **Reviewer** | Review queue, application assessment, document review and approve/reject/request-information decisions. |
| **Support agent** | Three-panel AI support workspace with inbox, conversation/composer, grounded AI copilot and a read-only knowledge workspace. |
| **Administrator** | User and role management, product administration and audit-trail inspection. |

### 3.2 Capability map

| Capability | Implemented outcome |
| --- | --- |
| Digital onboarding | Guided application from draft through submission, review, decision and optional resubmission. |
| KYC document handling | Validated upload, authenticated retrieval, review status and storage abstraction. |
| Workflow control | Server-enforced application state machine and ticket lifecycle. |
| Support operations | Filterable inbox, operational KPIs, conversation, internal notes, assignment, status changes. |
| Knowledge grounding | 26 approved articles, agent KB search/detail, scored citations with match reasons and safe draft workflows. |
| AI assistance | Structured summary, editable/regenerable suggested response, sentiment analysis, assistive classification and evidenced next-best actions. |
| Human oversight | AI output is advisory; status-changing recommendations require explicit confirmation and the recorded category is never auto-changed. |
| Security | JWT authentication, rotating refresh tokens, role-based authorization, upload validation, security headers and rate limiting. |
| Auditability | Append-only audit events, status history, ticket messages, assignment history and AI assistance records. |
| Notifications | In-app notifications and asynchronous outbox-based email delivery. |
| Administration | User roles, account activation, product catalogue and audit filtering. |
| Deployment | Local development workflow, Docker Compose stack and application preparation for a manually configured AWS environment. |

### 3.3 Value delivered

- **For customers:** a clear, guided onboarding journey with visible progress and
  fewer reasons to contact support.
- **For reviewers:** a consistent, controlled and auditable decision process.
- **For support agents:** faster triage, better context, more consistent replies
  and earlier identification of negative sentiment or escalation risk.
- **For the business:** improved operational efficiency, reduced response
  variance, stronger oversight and a reusable AI integration pattern.
- **For engineering:** a modular, testable codebase that can switch storage,
  email and AI providers through configuration.

### 3.4 Solution boundaries

The solution covers the application and support domains. It does **not** include a
real core banking integration, payment processing, a production KYC provider,
real malware scanning or infrastructure-as-code. These are explicitly documented
as limitations in [Section 13](#13-assumptions-limitations-and-roadmap).

## 5. Methodologies considered and selected

### 5.1 Delivery methodology

| Methodology | Characteristics | Assessment |
| --- | --- | --- |
| **Waterfall** | Sequential requirements, design, build, test and release. | Predictable but poorly suited to evolving assessment requirements and iterative AI integration. |
| **Agile Scrum** | Fixed sprints, backlog, ceremonies, incremental delivery. | Suitable, but full Scrum ceremony is heavier than necessary for a single delivery team. |
| **Kanban** | Continuous flow, work-in-progress limits, incremental releases. | Good for support operations, but less explicit for milestone-based assessment delivery. |
| **Iterative-incremental delivery** | Build vertical slices, verify each slice, refine subsequent work. | Best fit for evolving scope and continuous verification. |

**Selected methodology: Agile-inspired iterative-incremental delivery.**

The solution was delivered in vertical slices — authentication, onboarding,
documents, review, notifications, tickets, AI assistance, administration and
deployment — with each slice verified before the next was considered complete.
This provided early working software, reduced integration risk and allowed the
AI capability to be added without destabilising existing workflows.

### 5.2 Architecture methodology

| Approach | Characteristics | Assessment |
| --- | --- | --- |
| **Traditional layered monolith** | UI, business logic and data access separated only by technical layers. | Simple, but business rules become coupled to infrastructure and frameworks. |
| **Microservices** | Independently deployable services with separate data stores. | Strong isolation, but unnecessary operational complexity for this scope. |
| **Serverless** | Managed functions and event-driven services. | Attractive forelastic workloads, but introduces provider coupling and local-development complexity. |
| **Clean Architecture modular monolith** | Dependencies point inward; domain and use cases isolated from frameworks; ports for external concerns. | Best balance of maintainability, testability and delivery simplicity. |

**Selected architecture: Clean Architecture modular monolith with DDD-lite
domain modelling.**

The backend is split into Domain, Application, Infrastructure and API projects.
Dependencies point inward only. Domain behaviour is expressed on entities and in
the application state machine. External concerns — persistence, identity,
storage, email and AI — are abstracted behind ports and implemented by adapters.

### 5.3 AI methodology

| Approach | Characteristics | Assessment |
| --- | --- | --- |
| **Pure generative AI** | Send ticket context directly to a model and use free-form output. | Fast to prototype, but weak schema control, hallucination risk and no reliable offline path. |
| **Fine-tuned model** | Train a bespoke model on historical support data. | Requires representative labelled data, training infrastructure and ongoing evaluation; not justified for this scope. |
| **Vector RAG** | Embed a large corpus and retrieve semantically similar passages. | Valuable at scale, but unnecessary for this small approved catalogue and harder to explain to agents. |
| **Approved-KB grounding with deterministic retrieval** | Score 26 approved articles against ticket context and attach cited, explainable hits. | Chosen: no vector dependency, auditable match reasons and a replaceable retrieval port. |
| **Deterministic rules only** | Fixed rules for sentiment and recommendations. | Predictable and safe, but does not demonstrate generative assistance. |
| **Hybrid deterministic-first + provider abstraction** | Optional live model for summary, reply and sentiment; deterministic KB-grounded rules for classification and next-best actions; resilient fallback; human review. | Best fit for safety, reliability, offline operation and assessment requirements. |

**Selected AI methodology: hybrid, deterministic-first, human-in-the-loop
assistance behind a provider abstraction.**

Live inference is optional. The deterministic provider guarantees that the
application remains functional offline and in CI. The resilient provider wrapper
falls back automatically on timeout, transport failure or schema mismatch.
`AiAssistanceService` retrieves approved articles before generating any advisory
output. Issue classification and next-best actions are always produced by
deterministic rules over ticket context, sentiment, application state and KB
hits, never by an unreviewed model command.

### 5.4 Quality methodology

A risk-based test pyramid is used:

- **Domain unit tests** for state-machine and entity invariants.
- **Application service tests** against a real EF Core stack on in-memory SQLite.
- **HTTP integration tests** against the real application host.
- **Frontend unit tests** for client-side policy mirrors, safe AI drafts and
  endpoint wiring.
- **Live smoke tests** across the running API, KB grounding, masking and the
  security boundary.
- **Manual role-based verification** for end-to-end user journeys.

CI-style verification is reproducible from the repository root and must report
**PASS**, **FAIL** or **NOT VERIFIED** explicitly. Tests are not skipped or
weakened to obtain a green result.

## 6. Engineering approaches

| Approach | Implementation | Benefit |
| --- | --- | --- |
| **API-first contract design** | Typed request/response DTOs, OpenAPI/Swagger, RFC 7807 errors. | Stable client-server contract and testable endpoints. |

| **Responsive role-aware UX** | Shared design system, guarded routes, adaptive navigation and actions. | Consistent experience with defence in depth. |

## 7. Functional requirements and implemented features

### 7.1 Identity, authentication and authorization

| Requirement | Implementation |
| --- | --- |
| User registration and login | ASP.NET Identity with email and password. |
| Token-based authentication | JWT access token (15 minutes) and refresh token (7 days). |
| Refresh-token security | Single-use rotating refresh tokens; reuse is rejected. |
| Password policy | Minimum length 10; upper-case, lower-case and digit required; lockout after 5 failed attempts. |
| Role model | `Customer`, `SupportAgent`, `Reviewer`, `Administrator`. |
| Account administration | Administrators can assign roles and activate/deactivate accounts. |
| Route protection | API role checks at controller boundary; SPA route guards for defence in depth. |
| Cross-customer isolation | Access to another customer's application returns `404`, not `403`, to avoid leaking existence. |

### 7.2 Customer onboarding

| Requirement | Implementation |
| --- | --- |
| Product discovery | Authenticated catalogue of fictitious banking products with detail views. |
| Customer profile | View and update personal profile; profile completeness is required before submission. |
| Application creation | Customer creates a draft application for a selected product with structured answers. |
| Draft editing | Editable while the application is `Draft` or `AdditionalInformationRequired`. |
| Submission | Validates profile completeness, at least one answer and product minimum age. |
| Status tracking | Customer sees current status, status history, documents and reviewer requests. |
| Withdrawal | Customer can withdraw a draft application. |
| Resubmission | Customer can amend and resubmit when additional information is required. |

**Application lifecycle:**

```
Draft ──submit──► Submitted ──start──► UnderReview ──approve──► Approved
  │                   │                    │       ──reject───► Rejected
  │                   │                    └──request-info──► AdditionalInformationRequired
  │                   │                                              │
  └──────withdraw─────┴──────────────────────────────────────────────┴──► Withdrawn
                                                     addinfo ──resubmit──► Submitted
```

Terminal states (`Approved`, `Rejected`, `Withdrawn`) have no outgoing
transitions. Invalid transitions are rejected by the server.

### 7.3 KYC document management

| Requirement | Implementation |
| --- | --- |
| Document upload | Multipart upload associated with an application and document type. |
| Document types | Proof of identity, proof of address, proof of income, photograph and other. |
| Upload validation | Extension allow-list (`.pdf`, `.jpg`, `.jpeg`, `.png`), declared content type, magic-byte signature and 5 MB size limit. |
| Storage | Local file system by default; private S3 adapter available through configuration. |
| Retrieval | Authenticated content endpoint; presigned URL support when S3 storage is configured. |
| Review | Reviewers and administrators set `Pending`, `Approved`, `Rejected` or `NeedsReplacement`. |
| Scanning | Development scanner stub records `SkippedDev`; production malware scanning is out of scope. |

### 7.4 Review workflow

| Requirement | Implementation |
| --- | --- |
| Review queue | Filterable, searchable and paged queue for reviewers and administrators. |
| Application assessment | Full application detail including answers, documents and history. |
| Start review | `Submitted → UnderReview`. |
| Approve | Records decision reason, status, history, notification and audit event. |
| Reject | Records decision reason, status, history, notification and audit event. |
| Request information | Moves the application to `AdditionalInformationRequired` and allows customer resubmission. |
| Document review | Reviewers can approve, reject or request replacement of individual documents. |

### 7.5 AI-assisted support workspace

The support workspace is a dedicated three-panel experience:

1. **Inbox** — operational KPI strip, search, status/priority/sentiment filters,
   pagination and selectable ticket list.
2. **Conversation and composer** — ticket header, SLA indicator, assignment,
   message thread, public replies, internal notes and status changes.
3. **AI copilot** — summary, suggested response, sentiment, assistive
   classification and next-best actions, with cited KB sources, match reasons,
   provenance and safety disclaimers.

| Requirement | Implementation |
| --- | --- |
| Operations overview | `GET /api/tickets/overview` returns open, unassigned, urgent, escalated, awaiting-customer, resolved-today, assigned-to-me, negative-sentiment and analysed-sentiment counts. |
| Ticket filtering | Status, category, priority, assignee, free-text search and paging. |
| Conversation history | Chronological messages with customer, agent, system and internal-note presentation. |
| Public replies | Appended to the ticket; never overwrite history. |
| Internal notes | Visible to agents but excluded from AI context and customer-facing communication. |
| Assignment | Ticket can be assigned to the current agent; assignment history is append-only. |
| Status management | Ticket status changes are explicit and audited. |
| Sentiment filter | Inbox can be filtered by persisted sentiment; changing a filter resets paging to page 1. |
| KB workspace | `/knowledge` provides role-gated search, category filters, resolution steps and escalation criteria with the same codes cited by the copilot. |
| AI provenance | Every AI response displays live/fallback status, provider/model and review requirement. |
| Assistive classification | Suggested categories include matched signals and explanations; the persisted category is never overwritten. |
| Sensitive-action warning | The composer reminds agents to verify identity before acting on AI suggestions, and drafts never request credentials. |

### 7.6 AI assistance capabilities

| Capability | Endpoint | Output |
| --- | --- | --- |
| Structured summary | `POST /api/tickets/{id}/ai/summarize` | Main issue, key context, actions taken, outstanding items, current state, uncertainties and KB citations. |
| Suggested response | `POST /api/tickets/{id}/ai/suggest-response` | Subject, safe editable body, notes, review requirement and KB citations. |
| Sentiment analysis | `POST /api/tickets/{id}/ai/analyze-sentiment` | Label, explanation, confidence, escalation recommendation, signals, frustration indicators and urgency indicators. |
| Next-best actions | `POST /api/tickets/{id}/ai/next-best-actions` | Assistive classification plus ranked actions with title, explanation, priority, source articles, safe workflow, expected outcome, confidence and human-approval requirement. |

**Knowledge grounding:** every summary, suggested reply and action list carries
the approved articles that produced it. The agent can open `/knowledge` to verify
the cited guidance before copying or drafting a response. Article and ticket text
are treated as data, never instructions.

**Summary mapping:** the backend summary fields map directly to the six workspace
sections: Issue Overview, Customer Context, Actions Taken, Current Status,
Pending Resolution and Uncertainties.

**Suggested response behaviour:** the draft is editable, can be regenerated, can
be copied, and can be inserted into the composer as a public reply or an internal
note.

**Sentiment persistence:** the latest sentiment label and analysis timestamp are
stored on the ticket and exposed in ticket list, ticket detail and operations
overview responses. Automatic analysis runs when a selected ticket has no stored
sentiment.

**Next-best-action types:** `reply`, `request-documents`, `verify-identity`,
`review-application`, `escalate`, `resolve`, `follow-up` and `clarify`.
Actions that would change status (`resolve`, `escalate`) require an explicit
confirmation dialog and are never executed automatically.

### 8.3 Data model

Core entities:

`Application`, `ApplicationStatusHistory`, `CustomerProfile`, `KycDocument`,
`Product`, `Ticket`, `TicketMessage`, `TicketAssignment`, `Notification`,
`AuditEvent`, `OutboxMessage`, `RefreshToken` and `AiAssistanceRecord`.

Key relationships:

- `ApplicationUser` 1:1 `CustomerProfile` for customers.
- `Product` 1:N `Application`.
- `Application` 1:N status history and 1:N documents.
- `Ticket` 1:N messages and 1:N assignment history.
- Notifications, audit events, outbox messages, refresh tokens and AI records are
  standalone operational tables.

Design rules:

- Business-critical histories are **append-only**.
- Persisted references that must be valid use foreign keys; loose references that
  may intentionally outlive a user or entity do not.
- Ticket sentiment is stored as `LatestSentiment` plus `SentimentAnalyzedAtUtc`.

- List endpoints return `{ items, page, pageSize, totalCount, totalPages }`.
- Swagger UI is available at `/swagger` in Development.

## 9. AI design and safety

### 9.1 Provider architecture

```text
TicketsController
       │
       ▼
AiAssistanceService
       │  builds minimised ticket context
       │  queries approved KB and assistive classifier, then records metadata, citations and audit event
       ▼
ResilientAiProvider
       ├── AmazonBedrockAiProvider  (live, Converse API)
       ├── OpenAiCompatibleAiProvider (live)
       └── DeterministicFallbackAiProvider (default / fallback)
```

The live providers are wrapped by a resilient provider that falls back to the
deterministic implementation on timeout, transport failure or schema mismatch.
Knowledge retrieval and the assistive classifier run before the provider call;
their cited output is attached to the typed advisory result regardless of which
provider produced the prose.

### 9.2 Amazon Bedrock configuration

- Authentication uses the **AWS default credential chain** — environment
  variables, shared profile or workload/instance role.
- No AWS access keys or secrets are stored in the repository.
- Required permission: `bedrock:InvokeModel`; guardrail permissions are required
  when guardrails are enabled.
- Optional guardrails are configured with `Ai:GuardrailIdentifier` and
  `Ai:GuardrailVersion`.
- The default model is `anthropic.claude-3-5-sonnet-20241022-v2:0`; the model and
  region are configuration values.

### 9.3 Safety controls

| Control | Implementation |
| --- | --- |
| Untrusted input handling | Ticket text is supplied as delimited JSON data, never concatenated as instructions. |
| Prompt-injection defence | System prompt states that ticket content is untrusted and embedded instructions must be ignored. |
| Data minimisation | Last 20 public messages, 2,000 characters per message, 12,000-character context cap; internal notes excluded. |
| Role-gated application context | Related application references/statuses/document states enter AI context only for reviewers/administrators; agents get ticket-only context. |
| Typed outputs | Every capability returns a strongly typed contract, not free-form text. |
| Provenance | Responses include provider, model, live-inference flag, review requirement and disclaimer. |
| Human review | Every AI response is marked as requiring human review. |
| Sensitive-data guardrails | Prompts prohibit requesting or revealing passwords, OTPs, PINs and card numbers. |
| Outcome integrity | Prompts prohibit inventing statuses, timelines, fees, rates or policy. |
| Grounded sources | Summaries, replies and actions cite approved `KB-*` articles with match reasons; article text is data, not instructions. |
| Assistive classification | Suggested categories are advisory and never overwrite the persisted ticket category. |
| Deterministic recommendations | Next-best actions are produced by rules, not the model, and include safe human-confirmed workflows. |
| No privileged execution | AI cannot approve applications, change permissions or execute account actions. |
| Explicit confirmation | Resolve and escalate recommendations require a confirmation dialog. |
| Auditability | Each invocation records provider, model, live flag, input hash, output JSON, latency, confidence and actor. |

### 9.4 AI limitations

- AI output is advisory and may be incomplete or incorrect.
- Sentiment is an assistive signal, not a clinical or definitive assessment.
- The deterministic provider is intentionally rule-based and not a substitute for
  a live model.
- Deterministic keyword/field retrieval is tuned for the small demo corpus; a
  larger corpus should be evaluated against a vector index behind the same port.
- Model quality, cost and latency depend on the configured Bedrock model and
  region.
- A production deployment should add evaluation, monitoring, red-team testing and
  a formal responsible-AI review.

## 13. Assumptions, limitations and roadmap

### 13.1 Assumptions

- The application is an independent assessment and uses fictitious data only.
- Customers, reviewers, agents and administrators access the system through the
  same SPA but with different roles and permissions.
- Development uses SQLite, local file storage, no-op email and deterministic AI.
- Production providers are selected through configuration rather than code
  changes.
- A human remains accountable for all regulated, customer-affecting decisions.

### 13.2 Limitations

- **Local-first default.** The application ships configured for SQLite, local file
  storage, no-op email and deterministic AI.
- **No core banking integration.** There is no connection to account, payment or
  real KYC systems.
- **Development document scanner.** Malware scanning is a stub and reports
  `SkippedDev`.
- **No infrastructure-as-code.** AWS resources are configured manually; no
  `infra/` directory is included.
- **No formal performance SLO.** The solution has not been load-tested or tuned
  for a defined production throughput target.
- **No formal accessibility certification.** The UI is accessibility-conscious but
  has not been audited against WCAG 2.2 AA.
- **AI quality depends on provider.** Live model output requires evaluation,
  monitoring and human review.
- **No production secret management integration.** Secrets must be supplied by
  the deployment platform.

### 13.3 Recommended roadmap

1. Integrate a production identity provider and enterprise secret manager.
2. Replace the development scanner with a real malware-scanning pipeline.
3. Add a core banking/KYC integration and durable event bus for outbox delivery.
4. Introduce retrieval-augmented generation over an approved policy corpus.
5. Add AI evaluation datasets, red-team tests and production monitoring.
6. Add OpenTelemetry tracing, metrics and alerting.
7. Establish performance SLOs and run load, resilience and penetration tests.
8. Evaluate infrastructure-as-code and automated CI/CD promotion gates after the
   manual deployment is stable.
9. Complete a formal WCAG 2.2 AA accessibility audit.
10. Add data-retention, subject-access and deletion workflows.

## 14. Conclusion

Northstar Banking demonstrates a complete, secure and maintainable implementation
of a retail-banking onboarding journey and an AI-assisted support workspace. The
solution combines a controlled domain workflow, role-based security, auditability
and a provider-agnostic AI layer with deterministic fallback and human oversight.

The chosen iterative-incremental delivery method and Clean Architecture
modular-monolith design kept the scope deliverable while preserving clear
boundaries for future production concerns. The AI approach deliberately favours
safety, transparency and reliability over uncontrolled generation.

The delivered system is functional, documented, container-ready and verified by
**228 backend tests**, **37 frontend tests** and **97 live smoke checks**, with a
clean build and zero warnings. Live Bedrock inference remains unverified in this
environment; the deterministic fallback is the verified default. It provides a
credible foundation for a production-oriented onboarding and customer-support
platform.
